IOC(Indicator of Compromise)는 침해 의심을 확인할 때 대조하는 지표이다. 상관분석은 확인된 사용자·시간·순서 같은 조건으로 여러 기록의 관계를 확인하는 일이다.

이번에는 교육용 IP 목록과 감사 기록을 비교하고 실패 뒤 다운로드가 이어진 후보를 찾아보자. 지표값 일치와 사용자·시간 연결의 근거를 구분한다.

그림의 입력 자료에서 비교 기준을 거쳐 확인할 결과로 읽어 보자.

  • 일치한 원본 ID와 후보가 된 조건을 읽는다.
  • 다른 사용자·역순·시간 범위 밖·미확인을 제외한다.
  • 실패 2회와 3회 기준에서 결과 차이를 설명한다.

1단계. IOC 값이 일치하는 기록 찾기

indicators.json의203.0.113.66은 교육용으로 정한 IP다. 실제 악성 주소를 확인한 목록이 아니며 실습 결과에도 교육용이라고 표시한다. 입력 파일은 monitor/backend/learning/data에 있다. indicators.json은 대조할 IP 목록, audit-raw.json은 감사 원본 예제, actor-map.json은 확인된 사용자 대응표다. 준비된 감사 자료는 계정의 행동을 설명한다. ip 값이 목록에 있는지 확인하고 맞는 기록을 matches에 모으는 함수를 읽어 보자. checks.py — 준비된 IOC 대조 함수

def find_ioc_matches(events, indicators):
    matches = []
    for event in events:
        if event["ip"] in indicators:
            matches.append(event)
    return matches

in은 해당 값이 목록 안에 있는지 확인한다. matches.append(event)는 일치한 기록 자체를 남겨 원본 ID를 다시 읽을 수 있게 한다. 일치값과 의미 확인하기

  1. indicators.json에서 예제 IP 한 개를 확인한다.
  2. 감사 자료에서 IP가 일치한 기록이 곧 침해 확정인지 판단한다.
해설

값 일치는 추가로 검토할 신호다. 정상접속·공유IP·오래된지표 등 다른 설명이 있을 수 있으므로 IOC 일치만으로 침해를 확정하지 않는다.

2단계. 같은 사용자와 순서를 확인하기

준비된 대응표는 user-17과 mira@example.test를 employee-17로 연결한다. 이 확인된 공통 사용자 안에서 로그인 실패가 다운로드보다 앞에 있고 시간차가 5분 이내인지 검사한다. UTC(협정세계시)는 이 예제의 시각 기준이다. 같은 UTC 시각끼리 차이를 비교하며 한국 현지 시각으로 바꿔 계산할 필요는 없다.

원본 ID 시각(UTC) 공통 사용자 행동
a1 00:00:00 employee-17 로그인 실패
a2 00:00:30 employee-17 로그인 실패
a4 00:02:00 employee-17 다운로드

a1에서a4는 120초, a2에서a4는 90초이다. 둘 모두 먼저 일어났고 5분 이내이므로 실패 2회 뒤 다운로드라는 조건에 맞는다. checks.py — 준비된 순서 규칙

from learning.support import failures_before

def find_related_downloads(events, max_seconds=300):
    related = []
    for event in events:
        if event["kind"] == "download":
            failures = failures_before(event, events, max_seconds)
            if len(failures) >= 2:
                related.append({"download": event, "failures": failures})
    return related

failures_before는 확인된 같은 사용자의 먼저 일어난 실패 중 300초 이내인 기록을 골라 주는 준비 함수다. 시간 파서를 새로 만들지 않고 여기서는 len(failures) >= 2 조건을 읽는다. 연결 조건 예상하기

  1. 실패a1·a2와 다운로드a4의 사용자·순서·시간차를 확인한다.
  2. 실패가 한 번뿐이면 이 규칙에 맞는지 판단한다.
해설

실패 2회 이상이라는 조건이 있으므로 한 번으로는 맞지 않는다. 같은 IP라는 사실도 이 조건의 사용자 확인 근거를 대신하지 않는다.

3단계. 결과와 제외된 기록 대조하기

같은 저장소의 Windows CMD에서 준비된 lesson5.py를 실행한다. 사용자 대응표와 날짜 읽기는 준비 코드로 처리한다. Windows CMD

docker compose -f compose-monitor.yaml exec monitor-api python -m learning.lesson5
IOC 근거 ['a1', 'a2', 'a3', 'a4', 'a8']
연결 employee-17 ['a1', 'a2'] -> a4

IOC 일치 5건과 사용자·시간 후보 1건은 다른 규칙의 결과다. 같은 기록이 여러 규칙에 들어가므로 두 숫자를 더해 사건 6건이라고 말하지 않는다.

기록 순서 규칙에서 제외하는 이유
a5 다른 사용자 employee-23
a6 관련 실패에서 5분을 넘은 다운로드
a7 실패보다 먼저 일어난 다운로드
a8 IP는 같아도 공통 사용자 미확인

후보와 제외 근거 말하기

  1. a8이 IOC에는 있고 사용자·시간 후보에는 없는 이유를 말한다.
  2. a6의 시간을a1·a2와 대조해 5분 범위를 확인한다.
해설

a8은 값이 일치하므로 IOC 결과에 남지만 대응표에 사용자 근거가 없다. a6은00:08:00이므로 a1·a2 뒤 5분 범위를 넘는다. 서로 다른 조건을 읽어야 결과를 설명할 수 있다.

4단계. 실패 횟수 조건 바꾸기

VS Code에서 checks.py의 find_related_downloads 함수 안 len(failures) >= 2를 len(failures) >= 3으로 바꾸고 Ctrl+S로 저장한다. Windows CMD

docker compose -f compose-monitor.yaml exec monitor-api python -m learning.lesson5
IOC 근거 ['a1', 'a2', 'a3', 'a4', 'a8']
연결 결과 없음

같은 자료에서 실패가 두 번뿐이므로 3회 조건에는 맞지 않는다. IOC 대조 조건은 수정하지 않았으므로 일치 ID는 그대로다. 확인 뒤 len(failures) >= 2로 돌리고 저장한다. 마지막 화면은 실패 2회 조건을 사용한다.
